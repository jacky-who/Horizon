### [SemiAnalysis 实地探访内蒙古 800MW AI 数据中心园区](https://newsletter.semianalysis.com/p/we-visited-chinas-stargate-in-inner) ⭐️ 8.0/10

SemiAnalysis 在 9 月实地探访了内蒙古乌兰察布的 Galaxy 数据中心园区。该园区由风电系统集成商远景集团（Envision）拥有，规划 IT 容量最高达 800 兆瓦，核心规模与为 OpenAI 建设的美国 Stargate 阿比林园区相当。首期 120 兆瓦已在一年内交付，SemiAnalysis 称其成本仅为美国同类项目的五分之一，其余部分仍在施工中。四个阶段均为两家未具名的互联网巨头定制建设；据当地报道，周边察哈尔高新技术开发区在 22 个数据中心项目上共有近 3 万名施工人员。

rss · Semianalysis · 11月7日 19:01

**「背景」** 传统数据中心通常以交流电配电，再经多级变换供给服务器；800V 直流（800V DC）架构意在减少转换环节、提升效率并降低损耗。Envision 于 2026 年 11 月 2 日表示，其集成式 800V 直流供电系统已在乌兰察布 Galaxy AI 数据中心承载实际计算负载，并称这是大型 AI 数据中心首次商业部署此类系统。SemiAnalysis 本次探访的正是这座园区，它由全球风电装机超过 100GW 的 Envision 拥有并运营。

**「影响」** 对比较中美建设经济性的开发商而言，这个案例提供了一组具体基准：远景不仅运营数据中心，还自建风电场和专用供电线路，叶片工厂就在园区对面，并自行设计低压功率模块与 800V 系统、制造用于平滑负载的储能电池、共同设计预制变电站，这使得供电与配电环节可以在同一体系内压缩成本与工期。SemiAnalysis 同时指出，得州正面临有史以来最强的反数据中心情绪，而内蒙古仍在加速且没有类似阻力。由于四期容量都已为两家互联网巨头定制，其他客户能否获得同等条件的容量和价格，报道并未说明。

### [Asahi Linux 7.3 进展：Fedora Asahi Remix 首次同日发布](https://asahilinux.org/2026/11/progress-report-7-3/) ⭐️ 7.0/10

Asahi Linux 发布 7.3 进展报告，继续介绍 Apple Silicon 上的 Linux 支持工作；报告称 Fedora Asahi Remix 已在 Fedora Linux 45 于 11 月 3 日发布当天同步推出，这是该项目首次做到与上游同日发布，Fedora Asahi Remix 用户因此不必等待滞后的移植版本。报告发布后的讨论集中在仍缺失的 USB-C 外接显示器支持，以及项目对宽松许可证被第三方利用的担忧。还有评论者提到自称支持 Vulkan 1.4、M4/M5 和休眠的 Gravity Linux，但这些属于社区说法，未获所给材料独立验证。

hackernews · ackyshake · 11月7日 05:20 · [社区讨论](https://news.ycombinator.com/item?id=50401867)

**「背景」** Fedora Asahi Remix 是 Asahi Linux 为 Apple Silicon Mac 维护的 Fedora 发行版，其硬件支持来自 Asahi 对 Apple Silicon 平台的开发。该项目按 Linux 内核版本发布进度报告；据第三方整理，7.3 报告于 2026 年 11 月 7 日发布，署名 James Calligeros。

**「许可变更影响下游合规」** 直接影响落在许可合规上：据引述报告原文的报道，Asahi 已将全部仓库重新授权，原因是发现多起试图利用其原有宽松许可“劫持”项目、借 Linux on Apple Silicon 牟利的行为。依赖其代码的下游项目、再打包发行版与商业集成方需要按新条款重新核对授权范围，不能再沿用旧的宽松条款。

**「社区讨论」** 有评论者表示，USB-C 外接显示器支持是其暂不安装 Asahi Linux 的主要障碍，并意外新 CPU 支持会优先于该功能；另一名评论者则追问报告中提到的“利用宽松许可证”是否指 Omarchy，同时对项目曾采用 MIT 而非 GPL 表示意外。另有评论者宣传 Gravity Linux，声称其已让 Vulkan 1.4 工作、覆盖全部 M4 和多数 M5，并在完整 suspend-to-RAM 上取得显著进展，但这些功能声明尚未得到独立证实。

### [报告称 1,122 个公开 GitHub 文件含 Claude Code 密钥](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again) ⭐️ 7.0/10

一份安全报告称，与 Claude Code 本地设置相关的 1,122 个公开 GitHub 文件中存在密钥。评论指出，这并非“Don&\#x27;t Ask Again”操作本身导致，而是用户把 \`.claude/settings.local.json\` 提交到仓库，且其中手动批准的命令直接包含密码或密钥后才暴露。Claude Code 团队的 Boris（bcherny）回应称，该文件本应只留在本地，Claude 创建时会自动将其加入 gitignore；这些文件是手动创建并提交的，团队过去未做密钥清理，正在研究预防措施。

hackernews · shmulc · 11月7日 20:45 · [社区讨论](https://news.ycombinator.com/item?id=50407882)

**「背景」** Claude Code 在执行需要授权的命令时会请求确认；用户选择“Yes, and don&\#x27;t ask again”后，它会把该条命令的完整字符串写入项目内的 \`.claude/settings.local.json\`，以便之后不再询问。按设计，这个文件只应留在本地，Claude 自行创建时也会自动将其加入 \`.gitignore\`；但若用户手动创建并把它提交到公开仓库，被批准命令中内嵌的密码或 API key 就会随文件一并公开。

**「影响」** 对使用 Claude Code 的团队而言，实际风险集中在误把本地设置纳入版本控制：一旦该文件包含手动批准的命令和明文密钥并被推送，密钥就会进入公开仓库，需要从版本历史中清除并轮换。

**「社区讨论」** 评论普遍认为标题夸大了风险：Aurornis 指出，只有提交本地设置且其中命令含密钥时才会泄露。tsergiu 和 binarymax 则分享了降低代理权限的做法，例如按任务使用隔离虚拟机加 API 代理，或让 Claude 通过 1Password CLI 取用凭据。

### [分析称 macOS 内置未公开的个人关系图谱守护进程](https://8rank.ai/game/apple-intelligence-personal-knowledge-graph) ⭐️ 7.0/10

一项逆向分析声称，macOS 内置了未公开文档的守护进程，会在后台构建关于用户及其人际关系的“个人知识图谱”，涵盖用户身份、联系人关系、沟通方式和活动信息。该说法目前来自文章自身的分析，尚无苹果官方文档或独立验证予以确认，因此应视为对平台行为的指控，而非已证实的功能公告。对 Mac 用户而言，争议核心是系统后台收集与推断的范围，以及这些行为为何没有出现在公开说明中。

hackernews · infwhispers · 11月7日 09:46 · [社区讨论](https://news.ycombinator.com/item?id=50403097)

**「背景」** 据多家二手报道，macOS 自 13（2022 年）起就内置 knowledgeconstructiond 与 intelligenceplatformd 两个守护进程，它们在本机汇总用户身份、人际关系与通讯行为，构建一个可被查询的「个人知识图谱」，供 Apple Intelligence 的个性化功能检索使用（tool-2-1、tool-2-2）。这套机制的出现早于 Apple Intelligence 本身的发布，也就是说，相关数据汇集并非随新功能才引入；报道还提到研究者放出了让用户查看自身图谱的工具（tool-2-3）。本次讨论所称的「家庭成员分类器」，正建立在这一图谱之上。

**「影响」** 若该分析成立，隐私敏感用户和安全研究者不能只依赖系统设置中的可见选项来了解这类后台进程；在苹果补充文档或第三方复现之前，只能通过逆向分析和二进制审计核实其行为，平台透明度因此成为实际的操作问题。

**「社区讨论」** 有评论者从社会层面而非仅道德层面表达不安：即使对话参与者不介意被摘要，未被记住的内容也在塑造交谈语境，并提到若是可选加入（opt-in），这类数据或许还可接受。也有人表示 Photos 已能识别人脸和宠物，Mac 出现类似图谱并不意外；另有评论认为，LLM 辅助的逆向审计让未公开收集更容易被发现，但修改这些行为仍然困难。

### [MaxxBench 质疑 DeepSWE 高分是否可信](https://maxxbench.unlap.ai/research/why-maxxbench/) ⭐️ 7.0/10

MaxxBench 发布研究文章，面向使用 DeepSWE 评测的开发者质疑其高分是否可信，讨论集中在基准实现缺陷和较小模型过拟合。现有材料没有给出具体分数、受影响版本或修复时间，因此这目前是一篇评测有效性分析，而非已确认的基准结论。文章还引出对评测环境隔离的担忧：有评论指出，推理调用的 API 密钥被放在 agent harness 可访问的隔离环境内。

hackernews · antiuniverse · 11月7日 17:19 · [社区讨论](https://news.ycombinator.com/item?id=50406222)

**「背景」** DeepSWE 是用于评测前沿编码智能体的长周期软件工程基准：题目从零编写，覆盖 91 个仓库和 5 种语言，并由人工编写的验证器检查软件行为而非实现细节，官方将其定位为不受污染（contamination-free）的评测。因此，当有人质疑某一 DeepSWE 高分是否属实时，核心就在于这些题目、验证器和隔离环境能否阻止针对基准的过拟合，或防止评测缺陷被利用。

**「影响」** 对依赖 DeepSWE 榜单做模型选型的团队，直接后果是选型流程需要增加一道复核：先确认基准实现是否存在缺陷、评测环境是否真正隔离，再决定是否采信分数。

**「社区讨论」** 评论者 Systemerror7A69 称文章加深了他对 LLM 基准的怀疑，并对 DeepSWE 仍存在多个 bug 感到意外，还从中读出“不要使用 max 模式”的实用结论；rao-v 则认为更可能的问题在于实验室构建的 RL 环境过于简单，使小模型过拟合到这些环境，而非直接针对基准训练。kqr 还批评评测框架把 API 密钥放在 agent harness 可访问的隔离环境内，认为这是设计缺陷。

### [Coldframe：冒充超市冷柜控制器的 Python 蜜罐](https://github.com/hedgerow-dev/coldframe) ⭐️ 7.0/10

开发者发布开源项目 Coldframe，这是一个仅用 Python 标准库编写的单文件蜜罐，用来冒充 Danfoss AK-SM 800A 和 Dixell XWEB 超市制冷控制器。作者称，它通过复刻真实设备的响应头顺序、页面标题、证书字段和 TLS 版本，使这两个虚拟设备在 Shodan 上被识别为真实控制器，而不是蜜罐。它还能识别针对 CVE-2025-41450（Danfoss“当日代码”登录绕过）的尝试，并标记另外三个 Danfoss CVE 及 XWEB 漏洞；使用默认登录会进入一个带除霜按钮的假门店仪表盘。作者表示目前有两个实例上线约一天，只看到通用扫描器和 Shodan 爬虫，尚无真实攻击结果。

hackernews · hedgerow-dev · 11月7日 17:27 · [社区讨论](https://news.ycombinator.com/item?id=50406292)

**「背景」** Coldframe 所模拟并识别的 CVE-2025-41450，是 Danfoss AK-SM 8xxA 系列 4.2 之前版本中的认证不当漏洞；美国国家漏洞数据库（NVD）将其归类为 Improper Authentication。该漏洞与登录绕过有关，因此暴露在公网的这类制冷控制器会成为扫描和攻击尝试的目标。

### [GitHub 新 Git 存储架构 Rubicon 进入有限私有预览](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/) ⭐️ 7.0/10

GitHub 推出了代号 Rubicon 的新 Git 存储架构，面向大量 AI 智能体并发操作单个仓库的场景，目前处于有限私有预览阶段。GitHub 称，内部测试中该架构支持 5,000 个智能体同时协作，每秒处理 7,200 次推送，并保持较低读取延迟。架构上，Git 对象存入 Azure Blob Storage，引用状态由 Ref-CAS 管理，虚拟副本负责读写，后台节点压缩数据包。上述数字来自 GitHub 的内部测试，尚未经过独立验证，推广范围将逐步扩大。

telegram · zaihuapd · 11月7日 14:12

**「背景」** 在 Git 托管场景中，每次推送通常会生成新的 pack 文件，仓库规模越大，压缩、引用一致性和读写吞吐就越容易互相牵制。Rubicon 将对象数据放入 Azure Blob Storage，把引用与 pack 清单交给可复制的 Ref-CAS 日志，并用一次性虚拟副本承接请求、后台节点单独执行压缩，以此把存储和计算分离。

**「可用性限制」** Rubicon 目前仅处于有限私有预览，普通开发者和多数组织尚不能使用，因此 5,000 个并发智能体、7,200 次/秒推送是内部测试能力，而非已承诺的公开容量或 SLA；在扩大开放前，依赖高并发智能体操作仓库的团队不应据此调整生产容量规划。
