### [GitHub&\#x27;s Rubicon Git storage aims at 7,200 pushes per second](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/) ⭐️ 7.0/10

GitHub has introduced a new Git storage architecture codenamed Rubicon, aimed at many AI agents concurrently operating on a single repository. In internal tests, GitHub says it supported 5,000 agents collaborating at once and processed 7,200 pushes per second while keeping read latency low. The design stores Git objects in Azure Blob Storage, manages reference state with Ref-CAS, and uses virtual replicas for reads and writes plus background compaction of data packs. Rubicon is currently in limited private preview, with GitHub planning to expand it gradually.

telegram · zaihuapd · Nov 7, 14:12

**「Background」** GitHub’s previous Git storage layer, Spokes, coordinated writes through a three-phase commit, which limited write throughput. Rubicon changes that design by separating immutable Git objects stored in Azure Blob Storage from mutable references managed by a dedicated Ref-CAS service; a secondary report puts the new approach at up to 35x higher write throughput than Spokes.

**「Impact」** Organizations planning high-concurrency AI-agent workflows will have to wait for broader access: Rubicon is limited to private preview, so the 7,200-pushes-per-second figure is an internal test result rather than an available service-level guarantee.

### [An Engineer&\#x27;s Case for One Designer per Team](https://seangoedecke.com/working-with-designers/) ⭐️ 6.0/10

rss · Sean Goedecke · Nov 7, 00:00

**「Background」** Writing from engineering experience, Sean Goedecke argues that designers bring immediate, visible value and a healthy cultural distance from engineers, but that design work becomes dysfunctional when scaled like engineering.

**「Solution」** His central rule is one designer at a time: with three designers involved over the course of one product, he watched a good existing design be replaced, then each page revised three or four times as the designers reversed each other&\#x27;s changes until management froze the design near the deadline. He attributes this to design disagreements resting on taste rather than concrete measures like latency or bugs, and to design changes affecting the whole product because users experience it as one design. Design systems—shared libraries of compliant components—are his preferred but painful answer: owners are rewarded for components that always look elegant, while product teams must satisfy ugly requirements, so engineers reimplement components or patch CSS and then face compatibility gaps between the latest React system and older HTML/CSS or React versions. That mismatch forces engineers to translate desired features into what their version supports, though he still sees design systems as the best route to consistency across a large application that he has encountered. He also argues design is not always needed—APIs, billing, and rendering systems are technical, and poorly designed products like Netlify Analytics and Azure still succeed—so he wishes for a designer constantly but recognizes teams often lack one.

**「Takeaway」** The author&\#x27;s conclusion is that design&\#x27;s value is real but should be allocated narrowly—one designer where visual design matters—and that design systems, despite their costs, remain the least-bad way to keep a large product visually coherent.
